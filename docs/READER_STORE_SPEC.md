# Private reader store specification

Status: approved design, not provisioned
Machine-readable contract: `operations/reader-store.contract.json`

## Decision

Reader submissions move to a dedicated Supabase project. They live in a
`reader_private` Postgres schema that is not exposed through the Data API. The
browser submits through a narrow Edge Function; it never receives a Supabase
secret or direct table access. Row-level security remains enabled as defense in
depth, with no `anon` or `authenticated` table grants or policies.

This store replaces the published Google Sheet, committed `counter.csv`, the
reader-specific keys in `bakery-state.json`, and the `counter-sync` writer. It
also owns a short-lived private handoff bucket so unpublished content never has
to cross GitHub Actions' public logs or artifacts.

The project is dedicated to reader mail. This contains the blast radius of the
Edge Functions' server-side database authority and keeps growth analytics,
social credentials, and any future account data outside the reader boundary.

## Data model

### `reader_private.submissions`

One reader slip per row, with an immutable submitted payload and mutable
lifecycle fields:

- `id uuid` primary key generated by the database;
- `kind text`, exactly `ask_baker`, `king_letter`, or `crumb_pin`;
- `body text`, 1 to 2,000 Unicode characters after normalization while the
  payload is retained, then null only after a terminal retention or deletion
  transition records `payload_erased_at`;
- `byline text null`, at most 60 characters; null renders as anonymous;
- `submitted_at timestamptz` generated by the database, never trusted from the
  browser;
- `consent_version text` and `publication_consent boolean`, which must be true;
- `status text`, exactly one lifecycle state from the contract, including the
  short terminal-intent state `publishing`;
- `deletion_token_hash bytea`, SHA-256 of a 256-bit random token returned once;
- `reserved_batch_id uuid null`, `reserved_at timestamptz null`, and
  `lease_expires_at timestamptz null`;
- `published_edition_id text null`, `published_commit_sha text null`, and
  `published_at timestamptz null`;
- `rejection_code text null`, `deleted_at timestamptz null`, and
  `payload_erased_at timestamptz null`.

Checks enforce kind, state, length, consent, legal state combinations, and a
40-character lowercase hexadecimal publication SHA. Index `(kind, status,
submitted_at, id)` supports the oldest-first queue. No email address, account
identifier, raw deletion token, IP address, or user-agent is stored.

### `reader_private.plan_batches`

One idempotent reservation per morning edition:

- `id uuid` primary key, `edition_id text`, positive `attempt integer`, unique
  `(edition_id, attempt)`, and `slot text` fixed to `morning`;
- `status text`: `reserved`, `publishing`, `finalized`, `released`, or
  `expired`;
- `created_at`, `lease_expires_at`, and terminal timestamps;
- `published_commit_sha` and a non-secret verification receipt when finalized.

### `reader_private.plan_items`

This table is the durable relation between a batch and up to one submission of
each kind. `(batch_id, kind)` is unique. Partial unique constraints permit only
one live or finalized batch per edition and prevent a submission from belonging
to two live batches. Historical rows keep only opaque IDs and publication
facts after the payload retention period.

### `reader_private.audit_events`

Append-only operational events contain an opaque object ID, transition, time,
and machine actor. They must never contain reader text, bylines, deletion
tokens, request headers, or model output.

## Public submission boundary

`reader-submit` accepts only `POST` and `OPTIONS` from the two production site
origins in the contract. It applies exact JSON content type and body-size
limits, normalizes line endings and control characters, validates kind and
length, requires an explicit unchecked-by-default publication-consent box, and
verifies Cloudflare Turnstile server-side. A failed Turnstile check fails
closed. Generic responses do not disclose queue size or whether matching text
already exists.

The function uses its server-side Supabase secret only inside the Edge runtime.
No secret, table URL, service-role key, or deletion-token hash is emitted to the
page. A successful response returns an opaque receipt and the raw deletion
token once. The page tells the reader to save that token if they may want to
withdraw an unpublished submission.

The repository implementation uses a pooled Postgres connection authenticated
as a dedicated login that inherits the non-login `reader_edge` role. That role
has no table privileges and may execute only the allowlisted private transition
functions. Every privileged routine is kept in `reader_private`, uses an empty
`search_path`, and is revoked from `PUBLIC`, `anon`, `authenticated`, and
`service_role`. The public endpoints accept exactly `application/json`, cap the
complete request at 12,288 bytes, count Unicode code points after NFC
normalization, and do not send a network identifier to Turnstile or the store.

`reader-delete` accepts the raw deletion token, compares its SHA-256 digest in
constant time, and erases a pending or reserved payload. Deleting a reserved
item invalidates that batch, which cannot later pass publication authorization.
Once a batch enters `publishing`, the irrevocable publication boundary has
begun and the endpoint directs the reader to the public correction/removal
process. Removing a private row cannot erase an already public edition.

## Transactional plan boundary

`reader-plan` is not a public browser API. It requires a long random
`DDB_READER_BROKER_TOKEN` held only by trusted workflow steps and the Edge
Function. That token has no GitHub authority and is not a Supabase service key.
Rotate it on exposure and at least every 180 days.

`reserve(edition_id)` runs one database transaction:

1. lock or create the unique morning batch for that edition;
2. reclaim leases older than 120 minutes;
3. for each kind, select the oldest pending row with `FOR UPDATE SKIP LOCKED`;
4. mark no more than one row per kind reserved by this batch; and
5. return only those selected rows and opaque selection references.

Repeating `reserve` for the same edition returns the same live batch. A released
or expired attempt may create the next attempt number; a finalized edition can
never reserve again. The operation never returns the waiting queue, counts,
neighboring records, deletion hashes, or expired payloads. A different edition
cannot reserve a live row.

`authorize_publish(batch_id, manifest_digest)` is the short two-phase boundary
immediately before the GitHub token is minted. It rechecks consent, deletion,
lease, selection, and manifest state under lock, then moves the batch and rows
to `publishing`. `finalize(batch_id, edition_id, commit_sha, receipt)` succeeds
only after the publisher verifies that exact commit at remote `main`; it marks
the batch and selected rows published. `release(batch_id)` returns eligible
rows to the queue after a failed bake and completes a pending deletion instead
when needed. Cancellation is covered by lease expiry, so a lost runner cannot
strand the queue indefinitely. A `publishing` lease that expires raises an
incident for remote-SHA reconciliation before any row is released.

The renderer binds reader-visible text, byline, kind, and selection reference
to the reserved plan. The editorial model sees only the selected rows, treats
their text as quoted untrusted data rather than instructions, and cannot list,
swap, invent, finalize, release, or delete submissions.

## Private author-to-publisher handoff

Jobs run on separate fresh GitHub runners. Passing unpublished output through a
normal Actions artifact would expose it to readers of this public repository.
Instead, the broker creates a single-object signed upload URL for the private
`bake-handoffs` bucket. The author can upload one immutable bundle but cannot
list or read the bucket. The publisher obtains a short-lived signed download
URL in its fresh job, verifies the bundle digest and manifest, then deletes the
object. The object is uploaded with zero cache TTL; deletion, not URL expiry,
is the revocation control. A scheduled cleanup removes every handoff within six
hours even if a job is cancelled.

The bundle contains the base commit SHA, edition identity, allowed generated
paths, file digests, reservation ID, and generated public pages. It excludes
the raw reader plan, deletion token, Claude transcript, credentials, `.git`
state, executables, symlinks, and paths outside the allowlist. Diagnostics are
redacted summaries only. `content.json`, reader plans, and model logs are never
uploaded as public Actions artifacts.

The checked-in bucket contract caps objects at 10 MiB, accepts only ZIP or
generic binary MIME types, requires upload cache control `0`, gives signed
uploads the provider-fixed two-hour lifetime, and gives signed downloads 60
seconds. Object names contain only the opaque batch ID and bundle SHA-256.
Broker operations create upload/download capabilities, delete the exact object,
and remove every conforming object older than six hours without returning a
bucket listing.

## Repository implementation status

The local foundation lives under `supabase/` and is reproducible with the
pinned CLI and runtime dependencies in `package-lock.json`. It remains
unprovisioned. Deployment, canaries, and public-form cutover are blocked until
there is both an actually dedicated Supabase project and a verified
privacy-contact address. Neither value is represented by a guessed placeholder
in this repository. See `docs/READER_STORE_RUNBOOK.md` for verification and
operator sequencing.

## Retention and deletion

- Pending submissions expire and are erased after 90 days.
- Rejected payloads are erased within 30 days.
- Published private text and bylines are erased within 30 days after the public
  edition and its correction window are verified.
- Non-personal receipts containing opaque IDs, kind, timestamps, edition ID,
  and commit SHA may remain for 365 days, then are deleted.
- Unpublished deletion-token requests are completed immediately by automation;
  manual privacy requests are acknowledged and completed within seven days.

The public form must plainly say that accepted text and bylines can remain in a
public edition and git history after private-store deletion. A working private
contact at the project domain is a launch prerequisite; do not invent or print
an address until it exists.

## Required database tests

The deployed migration is incomplete until tests prove:

- `anon` and `authenticated` cannot select, insert, update, delete, or execute
  internal functions, even with guessed UUIDs;
- the public submitter can insert one valid row and cannot read it back;
- malformed, over-length, missing-consent, and bot submissions fail closed;
- concurrent reserves never select the same row and select at most one per
  kind, with stable oldest-first tie-breaking on `(submitted_at, id)`;
- retries within the same live edition attempt are idempotent, while released
  or expired attempts increment monotonically;
- deletion of a reserved row invalidates its batch, and publication
  authorization prevents the deletion/push race;
- finalize requires the reserved edition and a verified 40-character SHA;
- release and lease expiry make rows eligible again without duplicating audit
  history;
- no response, error, log, or handoff metadata contains a body or byline; and
- retention jobs erase payloads without breaking non-personal receipts.

Run Supabase's security advisors, performance advisors, RLS tests, and a clean
local migration before linking production. Pull the live schema after deploy
and require an empty diff. The July 2026 Supabase changelog was reviewed for
this design: do not pin extension versions, require current Node/TypeScript for
future tooling, and rely on explicit schema exposure rather than old automatic
Data API behavior.

## Cutover, rollback, and history

1. Create the dedicated project, private schema, functions, bucket, retention
   jobs, staging origins, alerts, and tests. No site traffic moves yet.
2. Import `counter.csv` once over a private channel. Reconcile the two existing
   reader dedup keys as already published and verify row counts and hashes.
3. Run synthetic submissions and two dry-run morning reservations. Prove
   reserve, release, finalize, expiry, deletion, and retention.
4. Deploy the new form with consent and Turnstile, then disable the Google Form
   and unpublish its Sheet in the same maintenance window.
5. Disable `counter-sync`, remove `counter.csv`, and remove reader keys from
   `bakery-state.json` in a reviewed forward commit. Keep only house-satchel
   state in the public repository.
6. Run one supervised morning bake and confirm the private queue, public
   edition, receipt, store finalization, and cleanup.
7. Install the publisher identity and protect `main` per
   `docs/PUBLISHER_IDENTITY_SPEC.md` only after its canary succeeds.

Rollback sends the site form to a temporary closed state, releases any live
batch, disables new reservations, and restores the last known-good site commit.
It never republishes the Sheet or recommits the queue.

Deleting `counter.csv` in a forward commit does not remove it from git history.
History rewriting is a separate destructive privacy operation with clone,
fork, Pages, cache, and force-push consequences. It requires an exact exposure
inventory, backup, user approval, GitHub support guidance, credential rotation
where relevant, and a maintenance window; this design does not authorize it.
